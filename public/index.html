Cluster Architecture

Control Plane & Worker Nodes

A Kubernetes cluster is split into a control plane (the brain, making global scheduling & state decisions) and one or more worker nodes (where your containers actually run). In managed offerings like AKS/EKS/GKE, the cloud provider hosts and patches the control plane for you — you only manage node pools.

Talking Points

How to explain this in an interview

Control plane, one line each

kube-apiserver — stateless REST front door; every component, including kubectl, only ever talks to the API server, never directly to etcd or kubelet.

etcd — distributed, consistent key-value store holding the entire cluster state; back it up, it is your cluster.

kube-scheduler — watches for unbound pods and binds them to nodes based on resource requests, taints/tolerations, affinity rules, and topology spread.

kube-controller-manager — runs reconciliation loops (Deployment, ReplicaSet, Node, Job controllers …) that continuously drive actual state toward desired state.

cloud-controller-manager — the piece that talks to the cloud provider API (Azure/AWS/GCP) for load balancers, routes, and node lifecycle — this is what AKS manages for you.

Node-level agents

kubelet — the agent that registers the node, receives PodSpecs from the API server, and instructs the container runtime to start/stop containers, reporting status back.

kube-proxy — programs iptables/IPVS rules so that a Service's stable ClusterIP load-balances to the right pod IPs.

Container runtime — containerd (or CRI-O) implements the Container Runtime Interface (CRI) that kubelet calls into.

Reconciliation is the core mental model: every controller runs an infinite observe → diff → act loop against etcd's desired state. Naming this loop explicitly is a strong interview signal.

GitOps / Pipeline

CI/CD to AKS — end to end

  1. Build a multi-arch image with Buildx; tag with the commit SHA (never latest).
  2. Push to ACR using OIDC federated credentials from GitHub Actions — no long-lived secrets in the repo.
  3. Authenticate to AKS in the workflow via az aks get-credentials (or a kubeconfig issued through workload identity).
  4. Deploy with Helm, Kustomize, or a GitOps controller (Argo CD / Flux) watching a manifests repo.
  5. Roll out gradually — canary or blue/green — gated by readiness probes and automated rollback on failed health checks.
This mirrors a secretless, OIDC-first pattern: the same federated-credential approach used for GitHub Actions → Azure App Service applies directly to GitHub Actions → AKS/ACR.
